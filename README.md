# 本地事件溯源：事件存储、投影同步、检查点与快照

一套**完全本地化**（内存或本地磁盘，不依赖任何外部服务/数据库/消息队列）的事件溯源
基础设施与示例域（银行账户），包含：

- 只追加（append-only）事件存储与乐观并发控制（OCC）；
- 事件结构演进（schema upcasting，历史事件永不改写）；
- 读模型增量投影、全量重建与检查点续跑；
- 幂等重放、乱序/重复/迟到事件防护、可定位且可重试的失败记录；
- 聚合快照、校验和、损坏/过期/缺失时安全回退到顺序全量重放；
- 覆盖上述全部场景的自动化测试（含 `-race` 并发测试）。

## 目录结构

```
eventstore/   事件存储接口 + 内存实现 + 本地文件（JSON-lines + CRC）实现
event/        事件注册表与 v1→v2→… 升级链（Upcaster）
snapshot/     聚合快照（版本定位 + CRC32 校验），内存/文件实现
projection/   检查点存储、投影器（增量/重建/幂等/失败重试）、模型状态存储
repo/         聚合仓储（加载、快照加速与回退、保存与快照整理）
bank/         示例域：账户聚合、v1/v2 事件、账户读模型
cmd/demo/     本地可运行端到端演示
internal/safeio/ 原子写（temp+fsync+rename）与文件名转义
```

## 快速开始

```bash
go run ./cmd/demo          # 端到端演示（使用临时目录，退出即清理）
go test ./...              # 全部测试
CGO_ENABLED=1 go test -race ./...   # 竞态检测
```

```
  model-states/<projection>.json   # 可选：读模型自身状态快照
```

## 核心概念与保证

### 1. 事件追加与乐观并发控制

每个已提交事件带两个顺序号：

- **流版本（Version）**：聚合流内从 1 开始、无空洞的序号；
- **全局位置（Position）**：跨所有聚合从 1 开始严格递增的序号，供投影/检查点使用。

追加按 `expectedVersion` 做乐观并发：

- `expectedVersion = 0`：流必须不存在；
- `expectedVersion = N > 0`：流当前版本必须正好是 N；
- 批量追加是原子的：要么全部按连续版本生效，要么一条都不进入已提交历史；
- 事件 ID 全局唯一，重复 ID 的追加被拒绝（批次内重复同样拒绝）。

冲突统一返回 `*eventstore.ConflictError`，其 `Reason` 字段可区分原因：

| Reason | 含义 |
| --- | --- |
| `stream_exists` | 想新建流，但流已存在 |
| `stream_not_found` | 期望流存在，但不存在 |
| `version_mismatch` | 基于过期版本写入（典型并发冲突），需重新加载后变基重试 |
| `duplicate_event_id` | 事件 ID 已提交（或批次内重复） |
| `empty_append` / `invalid_event` | 空批次 / 载荷非法 |

**被拒绝的写入不会进入事件流，也不会推进任何版本号。**

推荐的写入模式（见 `repo` 与集成测试）：加载 → 执行业务命令 → 保存；
收到 `version_mismatch` 后重新加载、把决策变基到新版本再保存。

### 2. 事件结构演进（兼容规则）

历史事件**以原始字节永久保存**；每次读取/重放时通过注册的升级链
（Upcaster）升级为当前结构。已提交的历史事件永不被改写。

演进规则（强约束）：

1. **只增不改**：新版本只能新增字段或重新解释默认值；不得改变已有字段语义；
2. 每个 `(事件类型, v → v+1)` 有且仅有一个**确定性纯函数** Upcaster
   （无 I/O、无时间/随机数、不修改输入），同一历史事件永远升级为同一当前事件；
3. **新增字段必须有确定默认值**，由 Upcaster 在旧载荷缺失（或显式 `null`）时填入；
4. **多余的未知字段原样保留**（读取宽容），解码器忽略不认识的字段；
5. 存储版本高于当前二进制可理解版本时，`Decode` 返回
   `*event.NewerSchemaError`（拒绝前向跳过，而不是静默错误）；
6. 未知事件类型返回 `*event.UnknownEventError`，路由型组件仍可看到信封，
   类型化解码显式失败。

示例（`bank` 包）：

| 事件 | v1 | v2 新增字段（默认值） |
| --- | --- | --- |
| `bank.account.opened` | `account_id, owner, currency` | `account_type="checking"`, `credit_limit=0` |
| `bank.money.deposited` | `amount, note` | `channel="unknown"`, `external_ref=""` |
| `bank.money.withdrawn` | `amount, note` | `channel="unknown"`, `reason_code="NONE"` |

默认值是业务中性值，保持 v1 语义不变（无授信额度、渠道未知、标准支票账户）。

### 3. 读模型增量处理与全量重建

投影器从检查点位置开始，按全局 Position 升序批量拉取并应用事件。

**全量重建（`Projector.Rebuild`）语义：**

1. 暂停该投影的增量循环（**仅暂停投影，事件追加始终不被阻塞**）；
2. 用模型工厂创建全新空模型，从 Position 0 开始无锁批量重放完整历史；
3. 重放期间新写入照常进入事件日志；
4. 重放完成后在独占锁内做一次“追赶”：把重放期间新提交的事件全部 drain，
5. 原子地发布新模型、新位置和检查点。

因为增量与重建走的是**同一条「升级 → 解码 → Handle」确定性管道**，重建结果
与长期增量处理的结果必然一致（有测试对逐字段相等做断言）。重建不会跳过任何事件。

### 4. 检查点与幂等重放

- 检查点记录“最后一个**成功处理**的全局位置”，每个事件处理成功后才推进；
- 处理失败时检查点停在失败事件之前，失败事件的位置/ID/聚合/错误信息通过
  `Projector.Failure()` 可定位，按指数退避自动重试；
- 修复后重试成功即继续；无法处理的毒消息可用 `Projector.SkipFailure()`
  显式确认并越过（返回被跳过事件记录，属于有意识的运维动作）；
- 重复/乱序/迟到事件的防护（应用到 Handle 之前）：
  - `Position <= 检查点位置` → `already_processed`（崩溃后重投递）；
  - 事件 ID 在有限记忆集合中 → `duplicate_id`；
  - 同一流的事件版本不大于已应用水位 → `regressed_stream_version`；
- 模型自身的 `Handle` 仍要求按事件 ID 幂等（示例 `AccountsModel` 内置
  AppliedEventID 集合），以覆盖“处理器成功、检查点未落盘”这一重投递窗口；
- 跳过原因通过 `Stats()` 与 `Options.OnSkip` 可观测。

**模型状态持久化（可选）**：实现 `projection.Stateful` 的模型可配置
`StateStore`（内存/文件），按间隔把模型状态与其包含位置一起落盘。
重启时同时恢复检查点与模型状态；状态落后于检查点时，从状态位置补放
（幂等），状态领先检查点则拒绝启动。未配置状态存储的模型重启后需 `Rebuild`。

### 5. 快照与历史整理

快照携带**足以定位事件流位置**的信息：`AggregateType / AggregateID / Version /
StateSchemaVersion`，另有 CRC32 校验和与时间戳。

仓储加载顺序：

1. 快照存在、身份/版本合法、未过期、未超出流末端、校验和正确、状态可反序列化
   → 恢复状态到 `snapshot.Version`，**只重放 Version > 快照版本的尾部事件**；
2. 快照**缺失**、**过期**（`MaxSnapshotAge`）、**损坏**（CRC 不符/JSON 非法）、
   指向流末端之后、与历史不相邻（版本空洞）或状态 schema 不认识
   → 放弃快照加速路径，**从版本 1 顺序重放全部事件，不跳过任何事件**；
3. 流为空则返回新聚合实例。

快照问题会通过 `Options.OnSnapshotWarning` 回调暴露（可记录/告警），但不会
让加载失败——全量重放始终是安全兜底。

保存时事件追加成功后，按 `SnapshotInterval` 周期性写快照（读路径上的“整理”；
事件日志本身只追加、永不重写）。快照写入失败只告警，不影响已提交的事件。

### 6. 本地持久化语义

- 事件日志：每行一个 JSON 记录（信封 + CRC32）。打开时全量校验：CRC、
  全局位置 1..N 无空洞、各流版本 1..M 无空洞、事件 ID 唯一；
  任何不符返回带**字节偏移**的 `CorruptionError`，不会静默截断。
- 追加：单批次一次 write + 一次 fsync；索引在打开时从日志重建，不存在索引漂移。
- 快照/检查点/模型状态：临时文件写入 + fsync + 原子 rename，
  读者永远看不到写了一半的文件。

## 运维手册（重建与恢复）

```go
// 正常增量处理（在后台 goroutine 中运行）
go proj.Run(ctx)

// 投影状态可疑、或部署了全新模型逻辑后：全量重建
if err := proj.Rebuild(ctx); err != nil { /* 事件历史本身有问题，见错误位置 */ }

// 某个事件持续处理失败：
if f := proj.Failure(); f != nil {
    log.Printf("blocked at position=%d event=%s aggregate=%s err=%s attempts=%d",
        f.Position, f.EventID, f.AggregateID, f.Err, f.Attempts)
    // 修复后无需操作：Run 会自动重试；
    // 或在人工对账后显式越过：
    // proj.SkipFailure(ctx)
}
```

- **进程重启（有 StateStore）**：自动恢复模型状态 + 检查点，补放二者间隙；
- **进程重启（无 StateStore）**：先 `Rebuild`，或接受空模型从头追赶；
- **快照损坏**：无需处理，加载自动全量重放；建议保留 warning 日志；
- **事件日志损坏**：打开存储即失败并给出损坏行偏移，需人工介入修复日志
  （系统不会悄悄丢事件）；
- **想“截断历史”**：当前实现不重写/截断事件日志。快照是读路径加速，
  全量历史始终保留，保证任意时点可重建。

## 测试覆盖

- `eventstore`：顺序与位置、五类冲突原因可区分、并发下同聚合恰好一个写入生效、
  带重试的并发追加得到无空洞 1..N、跨流全局位置无空洞、文件存储重启持久性、
  CRC 损坏检测（带偏移）、载荷字节不被读取改写；
- `event`：v1→…→当前版本升级链、缺失字段默认值、显式值不被覆盖、
  未知字段保留、确定性（两次升级字节一致）、更新版本拒绝、缺失链校验；
- `snapshot`：往返、缺失可区分、内存/文件两种损坏检测、替换语义；
- `projection`：检查点续跑不重复、重建与增量逐字段一致、重建期间持续写入不丢
  事件且不阻塞写入、失败定位+重试+退避+`SkipFailure`、瞬时失败自愈、
  文件检查点持久性；
- `repo`：快照加速与全量重放结果一致、损坏/过期/缺失快照回退、保存冲突拒绝
  与变基重试、并发保存带重试后版本与余额正确；
- 根目录集成测试：并发版本冲突、v1/v2 跨版本重放（内存与文件两套存储）、
  重建一致性、三种快照回退场景、跨“进程”重启（事件/快照/检查点/模型状态全本地恢复）。
